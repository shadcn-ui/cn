# cn build

`cn build` compiles the merge tables down to the classes your project
actually uses. It is the same contract as Tailwind's own content scanning:
classes found in your sources merge exactly like the default, and classes
that appear nowhere in your sources pass through untouched, which is
harmless because Tailwind generated no CSS for them either. The rules are
the ones Tailwind already imposes: don't build class names by string
concatenation, and use `--safelist` for exceptions.

## When to use it

You don't need a build step. The default import supports every Tailwind
class with zero setup, and that is the right choice for most projects. If
you're unsure whether you need `cn build`, you don't.

Reach for it when:

- you want the smallest bundle: it's the only mode smaller than tailwind-merge,
- you have a custom theme: baking it in at build time is free, while the
  runtime config entry costs ~15 KB,
- a build pipeline already exists and one script line is cheap.

Skip it for prototypes, for apps where 1.5 KB doesn't matter, and always in
published component libraries, where your consumers' classes aren't in your
corpus. Let the app make this call.

## Wiring it

`cn build` is a code generator: it must run before your bundler needs the
generated tables file. Wire it once, then never think about it. The run costs
a few hundred milliseconds.

In every setup below, the app code is the same:

```ts
// lib/utils.ts
import { createCn } from "cn/engine"

import tables from "./cn-tables"

export const cn = createCn(tables)
```

```gitignore
# generated by `cn build`
lib/cn-tables.ts
```

Patterns support `**`, `?`, and `{a,b}`; a pattern that names a dot-directory
or a normally ignored directory such as `out/` scans it; symbolic links are
followed.

## Next.js

Wrap your config. The tables are generated when `next dev` or `next build`
starts, before any module resolves, for webpack and Turbopack alike:

```ts
// next.config.ts
import { withCn } from "cn/next"

export default withCn(
  { reactStrictMode: true },
  { content: ["{app,components,lib}/**/*.{ts,tsx}"], out: "lib/cn-tables.ts" }
)
```

A function config works too: `withCn(async (phase) => ({ ... }), options)`.

If you'd rather not touch the config, npm lifecycle hooks do the same job
before `dev` and `build`:

```jsonc
// package.json
{
  "scripts": {
    "predev": "cn build --content \"{app,components,lib}/**/*.{ts,tsx}\" -o lib/cn-tables.ts",
    "dev": "next dev",
    "prebuild": "cn build --content \"{app,components,lib}/**/*.{ts,tsx}\" -o lib/cn-tables.ts",
    "build": "next build",
  },
}
```

The `.ts` output typechecks like any source file.

## Vite

Add the plugin next to Tailwind's. It generates the tables in `buildStart`,
which runs on every dev-server start and every build:

```ts
// vite.config.ts
import tailwindcss from "@tailwindcss/vite"
import { cn } from "cn/vite"
import { defineConfig } from "vite"

export default defineConfig({
  plugins: [
    tailwindcss(),
    cn({ content: ["src/**/*.{ts,tsx}"], out: "src/lib/cn-tables.ts" }),
  ],
})
```

Options are the CLI flags by name. `cwd` defaults to Vite's `root`.

## In dev

Both plugins watch your sources. A save that only reuses classes the tables
already know costs nothing. A save that introduces a class from a group the
tables dropped regenerates the file, which is a normal module, so the code
that imports it hot-reloads like any other edit. Deleting a file never
triggers a rebuild, since tables fitted to more classes are still correct.
Production builds always regenerate from scratch.

## Turborepo

`cn build` is deterministic — the same sources produce byte-identical
output — so it caches cleanly:

```jsonc
// turbo.json
{
  "tasks": {
    "cn-build": {
      "inputs": ["src/**/*.{ts,tsx}", "cn.config.mjs"],
      "outputs": ["src/lib/cn-tables.js"],
    },
    "build": { "dependsOn": ["cn-build"] },
  },
}
```

## From a script

`cn/build` is the function the CLI calls. Use it when a shell step doesn't
fit: a custom build script, a bundler plugin, a monorepo task runner that
wants a JavaScript API. Every CLI option is a field with the same name, and
errors throw with the message the CLI would print.

```ts
import { build } from "cn/build"

const result = await build({
  cwd: process.cwd(),
  content: ["src/**/*.{ts,tsx}"],
  out: "src/lib/cn-tables.ts",
})

console.log(`${result.usedGroups}/${result.totalGroups} class groups kept`)
for (const warning of result.warnings) console.warn(warning)
```

The result carries the written path, the emitted source, the candidate
tokens the tables were fitted to, and the group counts, so a caller can log,
cache, or decide when to rebuild.

## Custom themes

Add `--config` to the same command and the theme is baked into the generated
tables — no runtime config cost:

```bash
cn build --content "src/**/*.{ts,tsx}" --config cn.config.mjs -o src/lib/cn-tables.js
```

```js
// cn.config.mjs
export default {
  extend: { classGroups: { "font-size": [{ text: ["hero", "tiny"] }] } },
}
```

## The one gap to know about

With the npm-script setup, a class added mid-dev-session from a group your
project has never used before passes through unmerged until the next
dev-server start. Production builds are always in sync, since the `prebuild`
hook guarantees it. The Vite and Next.js plugins close this by watching your
sources, the same way Tailwind's scanner does.
