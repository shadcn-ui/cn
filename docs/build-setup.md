# cn build

`cn build` compiles the merge tables down to the classes your project
actually uses. It is the same contract as Tailwind's own content scanning:
classes found in your sources merge exactly like the default, and classes
that appear nowhere in your sources pass through untouched, which is
harmless because Tailwind generated no CSS for them either. The rules are
the ones Tailwind already imposes: don't build class names by string
concatenation, and use `--safelist` for exceptions.

## When to use it

You don't need a build step. The default import supports every Tailwind
class with zero setup, and that is the right choice for most projects. If
you're unsure whether you need `cn build`, you don't.

Reach for it when:

- you want the smallest bundle: it's the only mode smaller than tailwind-merge,
- you have a custom theme: baking it in at build time is free, while the
  runtime config entry costs ~15 KB,
- a build pipeline already exists and one script line is cheap.

Skip it for prototypes, for apps where 1.5 KB doesn't matter, and always in
published component libraries, where your consumers' classes aren't in your
corpus. Let the app make this call.

## Wiring it

`cn build` is a code generator: it must run before your bundler needs the
generated tables file. Wire it once, then never think about it. The run costs
a few hundred milliseconds.

In every setup below, the app code is the same:

```ts
// lib/utils.ts
import { createCn } from "cn/engine"

import tables from "./cn-tables"

export const cn = createCn(tables)
```

```gitignore
# generated by `cn build`
lib/cn-tables.ts
```

Patterns support `**`, `?`, and `{a,b}`; a pattern that names a dot-directory
or a normally ignored directory such as `out/` scans it; symbolic links are
followed.

## Next.js

npm lifecycle hooks run automatically before `dev` and `build`:

```jsonc
// package.json
{
  "scripts": {
    "predev": "cn build --content \"{app,components,lib}/**/*.{ts,tsx}\" -o lib/cn-tables.ts",
    "dev": "next dev",
    "prebuild": "cn build --content \"{app,components,lib}/**/*.{ts,tsx}\" -o lib/cn-tables.ts",
    "build": "next build",
  },
}
```

The `.ts` output typechecks like any source file.

## Vite

Scripts work the same way, or fold it into the config so it can't be
forgotten — regenerates on every dev-server start and build:

```ts
// vite.config.ts
import { execSync } from "node:child_process"
import { defineConfig } from "vite"

const cnBuild = () => ({
  name: "cn-build",
  buildStart() {
    execSync(
      "npx cn build --content 'src/**/*.{ts,tsx}' -o src/lib/cn-tables.js",
      {
        stdio: "inherit",
      }
    )
  },
})

export default defineConfig({
  plugins: [cnBuild()],
})
```

## Turborepo

`cn build` is deterministic — the same sources produce byte-identical
output — so it caches cleanly:

```jsonc
// turbo.json
{
  "tasks": {
    "cn-build": {
      "inputs": ["src/**/*.{ts,tsx}", "cn.config.mjs"],
      "outputs": ["src/lib/cn-tables.js"],
    },
    "build": { "dependsOn": ["cn-build"] },
  },
}
```

## Custom themes

Add `--config` to the same command and the theme is baked into the generated
tables — no runtime config cost:

```bash
cn build --content "src/**/*.{ts,tsx}" --config cn.config.mjs -o src/lib/cn-tables.js
```

```js
// cn.config.mjs
export default {
  extend: { classGroups: { "font-size": [{ text: ["hero", "tiny"] }] } },
}
```

## The one gap to know about

If you add a class mid-dev-session from a group your project has never used
before, stale tables pass it through unmerged until the next dev-server start
(production builds are always in sync — the `prebuild` hook guarantees it).
Restarting dev resyncs. The planned Vite/Next plugins close this by hooking
the file watcher, the same way Tailwind's scanner does.
